# TurtleBot3 Knowledge Navigation

ใช้ประจำสองโปรแกรมบน notebook: `create_knowledge.py` สร้าง knowledge และ `run_knowledge.py` นำไปใช้
ตัวนำทางเขียนเอง ไม่เรียก Nav2 ให้เดินแทน Program 2 มีหน้าจอแสดงผลในตัว ไม่จำเป็นต้องเปิด RViz2

## ตอนนี้ยังไม่มีหุ่น: ทดลองสองขั้นนี้

รันจากโฟลเดอร์ราก repository:

```bash
python3 tb3_knowledge/create_knowledge.py
```

1. กด **เลือก arena.yaml (+ PGM)** เลือก `~/tb3_maps/arena.yaml`
2. ถ้าไฟล์ PGM ย้ายที่ โปรแกรมจะให้เลือกแยก
3. โปรแกรมตรวจแนวกำแพงสี่ด้านอัตโนมัติ โดยแยกพื้นที่ unknown ที่ต่อกับขอบภาพออกจากพื้นที่ภายใน
   แล้ว fit สี่เหลี่ยมที่หมุนได้จากแนวผนังภายนอก เติม origin, width, height, yaw ให้เอง
   ดูกรอบสีเขียวบนภาพ หรือกด **ตรวจขอบสนามอัตโนมัติ** เพื่อคำนวณใหม่
   ปุ่มนี้ตรวจแล้วใช้กรอบที่พบให้ทันที ไม่ต้องกดใช้กรอบซ้ำ
   ถ้าผนังไม่ครบหรือหลักฐานไม่พอ จะขึ้นข้อความและใช้กรอบพื้นที่สำรวจชั่วคราวแทน
   กรณีนี้แก้ตัวเลขแล้วกด **ใช้ค่ากรอบที่แก้ไข** หรือเลือก **กรอบ 3 จุด** บนภาพ
   ปุ่มใช้ค่ากรอบอ่านค่าที่กรอกไว้ ไม่ได้ค้นหาผนังใหม่ และจะล้างผลฝึกเดิมพร้อมแนะนำ Start–Goal ใหม่
   ลำดับจุดคือมุมกำเนิด ปลายแกน x และจุดด้าน +y; โปรแกรมสร้างสี่เหลี่ยมโดยไม่ย่อ/ขยายสเกลแมพ
4. ตั้ง **ขนาดหุ่น / ระยะเผื่อ / ระยะถึง Goal** ในหน้า 1 ก่อนตรวจภารกิจ
   การเปลี่ยนค่าเหล่านี้จะยกเลิกผลฝึกและผลซิมใน session นี้ ต้องตรวจภารกิจและฝึกใหม่ ไม่ลบไฟล์ที่บันทึกไว้
5. คง **โหมดจำลอง — ยังไม่มีหุ่น** ไว้ เลือก Start/Goal บนภาพ และกรอกมุมหัน Start เป็นองศา
   ตัวเลขภารกิจอ้างอิงกรอบสนาม ไม่ใช่พิกัด map ดิบ: (0,0) คือมุมกำเนิดของกรอบ, x/y ตามแกนที่เลือก
   วงเส้นทึบรอบ Start และ Goal แสดงขนาดหุ่นตามรัศมีที่ตั้ง วงประรวมระยะเผื่อ ทั้งสองวงแสดงตามสเกลแมพ
   ค่าเริ่มต้นสำหรับ Burger / LDS-02 ใช้รัศมี 0.124 m รอบ `base_footprint` ครอบมุมท้ายของ collision box ใน URDF
   (`hypot(0.032 + 0.140/2, 0.140/2) ≈ 0.12371 m`) รวมระยะเผื่อ 0.040 m เป็นรัศมีปลอดภัย 0.164 m
   ตำแหน่ง LiDAR ในซิมคือ x=-0.032 m ตาม `base_link → base_scan`; หุ่นจริงอ่านตำแหน่งติดตั้งจาก TF
   อ้างอิง [Burger URDF](https://github.com/ROBOTIS-GIT/turtlebot3/blob/main/turtlebot3_description/urdf/turtlebot3_burger.urdf)
   หากติดอุปกรณ์เพิ่ม ต้องวัดรัศมีจากฐานอ้างอิงให้ครอบทั้งหมดและตั้งค่าใหม่
6. กด **ตรวจและใช้ Start–Goal** ดูข้อความยืนยันใต้ปุ่ม
   สีเขียว **ผ่าน** หมายถึงทั้งสองจุดวางหุ่นได้พร้อมระยะเผื่อ และมีทางเชื่อมที่ตัวหุ่นผ่านได้ในแมพ
   สีแดงอธิบายสาเหตุที่ไม่ผ่าน; เมื่อแก้จุด กรอบ หรือขนาดหุ่น ต้องตรวจใหม่
   ถ้ายังแก้ตัวเลขกรอบค้างไว้ ต้องกดใช้ค่ากรอบก่อนตรวจภารกิจ แล้วไปแท็บ **2. ฝึก / ส่งออก**
7. เลือกจำนวนชุดค่าที่จะลอง กด **สร้าง Knowledge** โปรแกรมทดลองให้ครบทุกชุดที่เลือก โดยไม่ต้องตั้งเวลาฝึก
8. กด **จำลอง: ค่าเริ่มต้น** หรือ **จำลอง: ใช้ Knowledge** เพื่อดูเส้นทางและผลของปุ่มที่กด
   ใต้แมพจะแสดงผลสำเร็จและตัวเลขขนาดใหญ่ของรอบล่าสุด: เวลา ระยะทาง ระยะห่าง Goal และการชน
   หน้าต่างกว้างเรียง 4 ช่อง หน้าต่างแคบเรียง 2 × 2 ช่อง เพื่อให้แผนที่และผลยังอ่านได้
9. กด **บันทึก knowledge.json** ค่าเริ่มต้นอยู่ที่ `tb3_knowledge/output/knowledge.json`

ระยะ Start ที่โปรแกรมแนะนำเป็นเพียงตัวอย่างวางหุ่นได้ในแมพ ไม่ใช่มุมสนามจริงที่วัดแล้ว
การตรวจขอบใช้แนวด้านในของกำแพง ไม่ใช้ขอบพื้นที่สำรวจเป็นกำแพงโดยอัตโนมัติ
แมพ arena ปัจจุบันตรวจได้ประมาณ 2.23×2.18 m มุม −6.35°; เป็นค่าประมาณจาก SLAM ไม่ใช่ค่าที่วัดจากสนามจริง
การตรวจใช้หลักฐานทั้งสี่ด้านและความต่อเนื่องตามแนวผนัง เพื่อไม่เลือกสิ่งกีดขวางกลางสนามเป็นขอบ
ความแม่นยำยังขึ้นกับความละเอียดและคุณภาพ SLAM กรอบ 3 จุดยังใช้แก้ผลตรวจได้
สีเทาคือ unknown โปรแกรมไม่ลบกำแพงหรือ unknown เพื่อสร้างทางผ่าน
หลังส่งออกจะล็อกการฝึก session เดิม เปลี่ยนสนามหรือภารกิจแล้วกดใช้ค่าเพื่อเริ่ม session ใหม่
การแก้ Start–Goal หลังฝึกต้องฝึกใหม่ก่อนส่งออก

### ตั้งค่าฝึกและอ่านผลซิม

- **จำนวนชุดค่าที่จะลอง 1–8:** โค้ดเตรียมพฤติกรรมการเดินไว้ 8 ชุด เช่น น้ำหนักมุ่ง Goal,
  clearance, ด้านอ้อม และการแก้ติดวน เลือก 4 หมายถึงลอง 4 ชุดแรก ชุดละ 2 seed
  ไม่ได้หมายถึงมี 4 พารามิเตอร์ ปุ่ม **ดูชุดค่าที่เตรียมไว้** แสดงค่าที่ต่างจากค่าเริ่มต้น
  จำนวน 8 เป็นขนาดรายการตัวเลือกที่กำหนดไว้ในโค้ด ไม่ใช่ข้อจำกัดทางทฤษฎีของอัลกอริทึม
  โปรแกรมทดลองครบจำนวนชุดที่เลือก แล้วประเมินแยก ไม่มีช่องตั้งเวลาฝึก
- **ค่าเริ่มต้นกับ Knowledge:** ใช้ตัวนำทาง KGGN ตัวเดียวกัน ต่างกันที่ชุดพารามิเตอร์
  Knowledge ใช้ชุดที่ถูกเลือกจากการทดลอง ไม่ได้รับตำแหน่งสิ่งกีดขวางเพิ่ม
- **ผลซิมล่าสุด:** กดปุ่มใดจะแสดงผลสำเร็จ เวลาในซิม [วินาที] ระยะเดิน [เมตร] ระยะห่าง Goal และการชนของรอบนั้น
  ใช้สนาม Start–Goal hardware และ seed 2026 เดียวกันทั้งสองแบบ
  เส้นสีน้ำเงินคือค่าเริ่มต้น สีชมพูคือ Knowledge แสดงเฉพาะเส้นทางล่าสุด
  ถ้าเปลี่ยนภารกิจหรือ hardware จะล้างผลเดิม ไม่ปะปนภารกิจต่างกัน
  หากชุดที่เลือกตรงกับค่าเริ่มต้น ผลอาจเท่ากัน และ Knowledge ไม่ได้ดีกว่าเสมอไป

ผลซิมจากปุ่มนี้แยกจากผลประเมินสอง seed ในสรุปการฝึก
เวลาที่แสดงคือเวลาการเคลื่อนที่ที่จำลอง ไม่ใช่เวลารอคอมคำนวณ
ถ้าไม่ถึง Goal เวลานี้คือเวลาที่จำลองจนหยุด พร้อมสถานะที่ระบุเหตุผล

**Robot ID** คือชื่ออ้างอิงที่ตั้งเอง เช่น `tb3` บันทึกอยู่ใน knowledge และต้องใช้ชื่อเดียวกันใน Program 2
มีหุ่นตัวเดียวใช้ค่า `tb3` เดิมได้ โหมด GUI ของ Program 2 อ่านชื่อนี้จากไฟล์ให้อัตโนมัติ
ชื่อนี้ไม่ใช่ IP, ROS namespace หรือหมายเลขประจำเครื่อง และไม่ได้เลือกการเชื่อมต่อ ROS ให้เอง
การตรวจหุ่นจริงยังอาศัยข้อมูลอ้างอิง odometry ที่ capture ไว้ด้วย

เปิด Program 2 แบบมีปุ่มเลือกไฟล์:

```bash
python3 tb3_knowledge/run_knowledge.py
```

กด **เลือกไฟล์ knowledge.json** แล้วเลือกไฟล์ที่บันทึกจาก Program 1
หน้าต่างจะแสดงขนาดสนาม Start–Goal และโหมดของไฟล์ การเลือกไฟล์ยังไม่เริ่มการทำงาน
ด้านขวาแสดงกรอบสนาม หุ่น จุด LiDAR สด ทางที่เลือกเฉพาะหน้า และรอยทางจาก odometry
ด้านล่างแสดงเวลา ระยะทาง ห่าง Goal และอายุ LiDAR ส่วนรายละเอียดข้อความอยู่แท็บ **รายละเอียด / Log**
สีเขียวคือหุ่น สีแดงคือ LiDAR สีชมพูคือทางที่เลือก และสีฟ้าคือรอยทางจาก odometry
กรอบสนามมาจาก knowledge ส่วนสิ่งกีดขวางมาจากเซนเซอร์ระหว่างรันเท่านั้น
ตอนยังไม่มีหุ่น กด **ทดลองจำลอง — ยังไม่มีหุ่น** เพื่อเปิดซิม และกด **หยุด / ปิดการทดลอง** เพื่อจบ
ไฟล์ simulation จะปิดปุ่มเดินจริงไว้ ส่วนปุ่มตรวจเซนเซอร์และเดินจริงใช้เมื่อมีหุ่นแล้ว
ปิดหน้าต่างหลักระหว่างทดลองจะขอให้โปรแกรมที่เปิดอยู่หยุดก่อน

ยังใช้ CLI ตรวจไฟล์ได้โดยไม่เปิด ROS:

```bash
python3 tb3_knowledge/run_knowledge.py --inspect
```

หรือดูหุ่นจำลองเดินใน **สนามสมมติใหม่**:

```bash
python3 tb3_knowledge/run_knowledge.py --demo
```

`--demo` ไม่อ่านแมพ SLAM จึงไม่ใช่สิ่งกีดขวางชุด arena เดิม
หากต้องการดูผลบนแมพเดิม ใช้ปุ่มจำลองใน Program 1
ทดสอบไม่มีหน้าต่างใช้ `--demo --no-window`
ถ้าบันทึกชื่ออื่น เพิ่ม `--knowledge /path/to/knowledge.json`
ไฟล์โหมดจำลองใช้ `--drive` ไม่ได้ ต้องกลับมาเตรียม reference ของหุ่นจริงใน Program 1

## Knowledge เก็บอะไร

ค่าเริ่มต้น Burger ใช้รัศมีตัวหุ่น 0.124 m + ระยะเผื่อ 0.015 m,
ความเร็วเดินสูงสุด 0.05 m/s และหมุนปกติสูงสุด 0.5 rad/s
ตัวจำลองและ runtime ใช้ค่าชุดเดียวกันจาก Knowledge; ไฟล์เก่ายังต้องปรับผ่าน serializer หรือส่งออกใหม่
กรอง NaN ที่ขาดต่อกันไม่เกินสองจุดและช่วงระหว่างจุดวัดขนาบไม่เกิน 5°
เฉพาะเมื่อระยะสองข้างต่างกันไม่เกิน 0.05 m และทั้งคู่ห่างอย่างน้อย 0.25 m
ใช้ระยะด้านใกล้ลบ 0.02 m และเพิ่มระยะเผื่อจากช่วงลำแสงเต็มช่องที่กรอง
นี่เป็นการประมาณผิวต่อเนื่อง ซึ่งอาจไม่เห็นวัตถุเล็กที่ซ่อนในช่อง ไม่ใช่การยืนยันพื้นที่ว่างจากเซนเซอร์
หน้า Program 2 แสดงจำนวนช่องที่ประมาณแยกจากประวัติสแกน; เปอร์เซ็นต์ 90% ยังคิดจากข้อมูลดิบ

หน้า “สนาม / เซนเซอร์สด” แสดงกล่อง “เงื่อนไขที่ยังติด” เหนือสนาม
หนึ่งบรรทัดต่อหนึ่งข้อ พร้อมค่าปัจจุบัน/เกณฑ์และอายุผลตรวจ เช่น `86.0%; ต้อง ≥90%`
เรียงข้อไม่ผ่านก่อนข้อยังตรวจไม่ได้ และเลื่อนอ่านได้ทั้งแนวตั้ง/แนวนอน
ข้อที่ผ่านแล้วหายจากกล่องนี้; รายละเอียดทั้งหมดรวมข้อผ่านยังอยู่ในแท็บเงื่อนไขการเดิน

โหมดระยะเผื่อต่ำใช้จุด LiDAR ที่วัดได้จริงนำทาง เมื่อข้อมูลดิบครบอย่างน้อย 90%
ช่องลำแสงที่ขาดจะยังแสดงบนหน้าจอ แต่ไม่สร้างสิ่งกีดขวางเสมือนใกล้ตัวหุ่น
จุดวัดจริง ขอบสนาม footprint ระยะเบรก freshness reference และ guard ยังบังคับใช้
จึงอาจพลาดวัตถุแคบหรือวัสดุที่ LiDAR วัดไม่ได้ในช่องข้อมูลที่ขาด

ค่าเริ่มต้น `odom_timeout` เป็น 0.5 s; ไฟล์ Knowledge เดิมใช้ค่าที่บันทึกไว้ใน `hardware`
การปรับไฟล์ต้องบันทึกผ่าน `Knowledge.save()` เพื่อคำนวณ fingerprint ใหม่
เมื่อไม่มีมุม unknown คงค้าง เลือกช่องทางสั้นที่ยืนยันระยะได้ตั้งแต่ 0.05 m
หลังหักวงหุ่นและระยะเผื่อ โดยยังตรวจแนวเคลื่อนที่และระยะเบรกตามเดิม
ถ้ายังมี unknown ใช้เกณฑ์เดินปกติเดิมและก้าวเก็บสแกนแบบจำกัดระยะ/เวลา
มุม unknown ที่ทับวงปลอดภัยยังหยุดการเดินหน้า ไม่ใช้กรอบสนามแทนหลักฐานพื้นที่ว่าง
การหมุนเก็บสแกนอยู่กับที่ใช้รัศมีตัวหุ่น 0.124 m + 0.002 m + ระยะหยุดไหลที่คำนวณจาก odometry
แทนระยะเผื่อการเดิน 0.04 m เฉพาะการตรวจ unknown และจำกัดความเร็วหมุน 0.15 rad/s
จุดวัดสิ่งกีดขวางจริงและขอบสนามยังใช้ระยะเผื่อเดิม รวมระยะหยุดไหล
ความคลาดเคลื่อนของขนาดหุ่น/ตำแหน่ง LiDAR หรือของที่ยื่นนอกตัวหุ่นกระทบเกณฑ์หมุนที่ลดลงนี้

ไฟล์เดียวมีกรอบพิกัดสนาม, Start `(x,y,yaw)`, Goal, policy 12 ค่า, hardware,
initial reference ของ odometry, ผลรวมการฝึก และ fingerprint
**ไม่มีตำแหน่ง รูปร่าง จำนวนสิ่งกีดขวาง occupancy grid หรือเส้นทางที่สำรวจไว้**
กรอบสนามหมายถึงรู้ขอบเขต ไม่ใช่รับรองว่าพื้นที่ข้างในโล่ง
Program 2 อ่านเพียง JSON นี้กับเซนเซอร์สด ไม่โหลด PGM/YAML หรือใช้ AMCL ระหว่างนำทาง

Policy คือ goal/clearance/turn/revisit weights, ด้านอ้อมเริ่มต้น, ระยะอ้างอิงเดินตามขอบ,
ระยะลดความเร็ว, hysteresis, เวลารักษาด้านอ้อม, ช่วงวัดความคืบหน้า, ความคืบหน้าขั้นต่ำ และ lookahead
Program 1 ทดลอง 1–8 ชุดพารามิเตอร์สำหรับ Start–Goal ที่ระบุ โดยใช้สอง seed ต่อชุด
เลือกจากการไม่ชนและถึงเป้าหมายก่อน แล้วจึงเทียบเวลา/ระยะทาง
ทดสอบชุดที่เลือกกับค่าเริ่มต้นด้วย seed ใหม่สองค่า ซึ่งไม่ถูกใช้เลือกพารามิเตอร์
ทดลองให้ครบทุกชุดที่เลือก แล้วประเมินแยกโดยไม่ใช้เวลาจำกัดการฝึก
รายงานรายละเอียดอยู่ `output/training_report.json`; ไม่ต้องส่งให้ Program 2

## Algorithm

KGGN เป็นชื่อโครงงาน ไม่ใช่การอ้างความใหม่ทางวิชาการ
อ่าน LiDAR แล้วตรวจช่องว่างด้วยขนาดตัวหุ่น ระยะเผื่อ ความละเอียดลำแสง กรอบสนาม และระยะหยุด
ตัวเลือกที่ผ่านเงื่อนไขจึงถูกให้คะแนนตามทิศ Goal, clearance, การเลี้ยว และการย้อนทางเดิม
มีโหมด GOAL, FOLLOW และ RECOVER พร้อม hysteresis และจำนวน recovery สูงสุด
คำนวณ linear/angular velocity เอง ส่งผ่าน ROS; ไม่ใช้ `NavigateToPose` หรือ Nav2 planner/controller
ไม่รับประกัน shortest path หรือถึง Goal ทุกสนาม
Simulator แยก true pose กับ odometry estimate มี dynamics, delay, range noise และ drift แบบจำลอง
ผลซิมสำเร็จเมื่อ true pose อยู่ใน goal_tolerance ที่กำหนด ไม่มีการขยาย tolerance เพื่อให้ผ่าน
การหยุดคาดการณ์เล็งที่ 80% ของ tolerance เพื่อเผื่อความคลาดเคลื่อน; ของจริงยังต้องสอบเทียบ

### Program 1: เตรียม Start จริง

1. โหลดแมพและกำหนดสนามเหมือนช่วงจำลอง เอาเครื่องหมายโหมดจำลองออก
   โหมดหุ่นจริงไม่มีการคลิก Start คร่าว ๆ หรือรัศมีค้นหา ช่อง Start อ่านอย่างเดียวจนรับตำแหน่งจาก ROS
2. วาง **หุ่นที่จะเดินจริง** ที่ Start แล้วกด **เปิด Localization / หาตำแหน่งอัตโนมัติ**
   โปรแกรมเปิด Map server + AMCL + RViz แล้วค้นหาตำแหน่งทั่วแมพจาก LiDAR โดยหุ่นอยู่นิ่ง
   โปรแกรมไม่เปิด Nav2 navigation controller และไม่ส่งคำสั่งมอเตอร์ในขั้นนี้
   ถ้าปิดเฉพาะหน้าต่าง RViz กดปุ่มเดิมเพื่อเปิด RViz ใหม่ได้ โดยใช้ AMCL session เดิม
3. ไม่ต้องกด **2D Pose Estimate** ก่อนเริ่ม รอสถานะการค้นหาใน Program 1
   โปรแกรมเรียก `/reinitialize_global_localization` เมื่อมีแมพตรงกับไฟล์ที่เลือก, AMCL active,
   odometry สด และ LiDAR มีจุดจริงเพียงพอ จากนั้นเรียก `/request_nomotion_update` เป็นช่วง ๆ
   เพื่อให้ filter ประเมินสแกนต่อได้โดยไม่ต้องขยับหุ่น
   อีกขั้นจะเทียบสแกนกับตำแหน่งและทิศทั่วแมพ แล้วขยายความละเอียดบริเวณที่ได้คะแนนดี
   ตรวจทั้งปลายลำแสงกับผนังและระยะที่แมพคาดว่าจะอ่านได้ หากตำแหน่งที่ดีที่สุดแยกจากคำตอบอื่นชัดเจน
   และอย่างน้อย 90% ของลำแสงที่ใช้ตรงแมพภายใน 10 ซม. (หรือสองพิกเซลเมื่อหยาบกว่า)
   จะส่งผลผ่าน `/set_initial_pose` ให้ AMCL ตรวจต่อ ไม่อาศัยความมั่นใจของ AMCL อย่างเดียว
   การค้นหาทั่วแมพนี้ใช้เฉพาะ Program 1 และจำกัดแมพ 250,000 พิกเซล / จุดค้นหาเริ่มต้น 15,000 จุด
   หากสแกนรอบแรกไม่พอ/ไม่ผ่าน หรือยังแยกตำแหน่งไม่ได้ จะลองสแกนใหม่อัตโนมัติห่างกันอย่างน้อยประมาณ 1 วินาที
   ภายในช่วงค้นหา 45 วินาที โดยค้นหาทั่วแมพและไม่ลดเกณฑ์ยืนยันตำแหน่ง หน้าจอแสดงจำนวนรอบที่ลอง
4. ตรวจแนว LiDAR ใน RViz ระหว่างค้นหา แล้วรอ **พร้อม=True**
   เมื่อผ่าน โปรแกรมจะปิดเฉพาะหน้าต่าง RViz ที่ตนเปิดให้อัตโนมัติ AMCL ยังทำงานต่อเพื่อรับ Start/ส่งออก
   โปรแกรมตรวจ freshness, covariance, น้ำหนักอนุภาคอย่างน้อย 95% อยู่ใกล้ตำแหน่ง/ทิศเดียวกัน
   และผลประมาณนิ่งต่อเนื่องอย่างน้อย 1.5 วินาที ไม่ถือว่า pose แรกแม่นยำทันที
   ต้องมีอย่างน้อย 4 ผลประมาณในหน้าต่าง 4 วินาที เพื่อรองรับ AMCL ที่อัปเดตไม่สม่ำเสมอ
   ทุกผลในหน้าต่างต้องห่างจากผลล่าสุดไม่เกิน 2.5 ซม. / 0.07 rad และยังตรวจ freshness แยกตามเดิม
   ระหว่างรอ หน้าจอแสดงจำนวนผล ช่วงเวลา และค่าการแกว่งของตำแหน่ง/ทิศ เพื่อบอกว่าติดเกณฑ์ใด
5. กด **เชื่อม ROS / รับตำแหน่ง Start** เพื่อรับ Start ที่หาได้
   ถ้าค้นหายังไม่จบ ปุ่มนี้จะแจ้งเหตุผลและไม่รับ Start
6. เลือก Goal แล้วสร้าง knowledge ตำแหน่ง Start ต้องตรงกับที่ capture
7. ส่งออก; โปรแกรม capture pose/odom ซ้ำอย่างสอดคล้องกัน ถ้าตำแหน่งเปลี่ยนเกินเกณฑ์จะไม่ให้ส่งออก
8. กด **หยุด Localization ก่อนเปิด Program 2** หรือปิด Program 1
   หากเปิด AMCL/SLAM เองต้องปิดด้วย จากนั้นให้หุ่นอยู่นิ่ง ห้ามย้ายหุ่นหรือ reset bringup/odometry
   Program 1 จะเก็บกวาด localization ที่ตนเปิดเมื่อออกตามปกติ หรือได้รับ Ctrl+C / SIGTERM

ถ้ายังยืนยันไม่ได้ภายในประมาณ 45 วินาทีหลังเริ่มค้นหา โปรแกรมจะแจ้งให้ลอง **ค้นหาตำแหน่งใหม่ทั่วแมพ**
หรือช่วยด้วย **2D Pose Estimate** ใน RViz โดยไม่ได้สุ่มเลือก Start ให้เอง
การค้นหาอัตโนมัติอาจแยกมุมไม่ได้ในสนามสี่เหลี่ยมที่สมมาตรหรือ LiDAR เห็นสิ่งกีดขวางไม่พอ
ความนิ่งและน้ำหนักอนุภาคเป็นความมั่นใจของ filter ไม่ใช่หลักประกันว่าตรงตำแหน่งจริงเสมอ จึงควรตรวจแนวสแกนด้วย
การค้นหาใหม่จะล้าง Start/reference และผลฝึกเดิม ต้องรับ Start แล้วสร้าง knowledge ใหม่
([AMCL global/no-motion services](https://github.com/ros-navigation/navigation2/blob/jazzy/nav2_amcl/src/amcl_node.cpp))

การใช้แมพเต็มเพื่อ localize ก่อนเริ่มเป็นแนวทาง setup ที่เสนอ หากข้อกำหนดอาจารย์ห้ามให้เปลี่ยนเป็น Start ที่วัดเอง
ขณะนี้ UI live workflow ใช้ AMCL; ไม่ควรแก้ reference ใน JSON เพื่อข้ามขั้นตรวจ

ถ้า RViz ไม่แสดงหุ่น ให้ตรวจ display **TurtleBot3** เปิดอยู่ และรับ `/robot_description`
ส่วน **Fixed Frame** ใช้ `map` สำหรับ localization ต้องมี TF ต่อกันเป็น
`map → odom → base_footprint → base_link` และ `base_link → base_scan`
ถ้า `/scan` กับ `/odom` มา แต่ยังไม่มี `/amcl_pose` ให้ดูสถานะค้นหาอัตโนมัติใน Program 1 ก่อน
หากค้นหายังแยกตำแหน่งไม่ได้ ใช้ **2D Pose Estimate** ช่วยตั้งต้นได้
Program 1 ตรวจ ROS graph โดยตรงก่อนเปิดชุดใหม่ เพื่อป้องกัน AMCL/map_server ซ้ำจากข้อมูล daemon ที่ค้าง

รายงาน **เงื่อนไข Localize** อยู่ด้านขวาและเลื่อนอ่านได้ แสดง condition ที่ติด พร้อมค่าปัจจุบันเทียบเกณฑ์
ครอบคลุมอายุข้อมูล แมพ ความนิ่ง covariance กลุ่มสมมติฐาน คะแนนเทียบสแกน และระยะ/มุม AMCL จากตำแหน่งตั้งต้น
แม้หมดเวลา รายงานยังแสดง condition ต้นเหตุไว้ ไม่แสดงเพียงข้อความ timeout

ทุกปุ่มแสดงผลด้านบน: **กำลังทำงาน / ผ่าน / ไม่ผ่าน / ยกเลิก** พร้อมรายละเอียดในแถบสถานะ
การเปิด Localization สำเร็จเป็นผลของปุ่มเปิดระบบ ต้องรอผล **Localize สำเร็จ** ก่อนรับ Start
การฝึก/จำลองจะแสดงกำลังทำงานก่อน และแจ้งผลหลังจบ ไม่ถือว่ากดเริ่มแล้วสำเร็จทันที

### Program 2: รับเซนเซอร์และวิ่ง

เปิดหน้าจอหลัก แล้วเลือกไฟล์ knowledge ล่าสุด:

```bash
python3 tb3_knowledge/run_knowledge.py
```

กด **ตรวจเซนเซอร์ ROS — ไม่สั่งมอเตอร์** แล้วดูตำแหน่งและจุดสแกนในหน้าเดียวกัน
ปุ่มนี้ไม่สร้าง publisher คำสั่งความเร็ว เมื่อตรวจแล้ว กด **หยุด / ปิดการทดลอง** รอปิดครบ
จากนั้นกด **เริ่มเดินจริง** โดยหุ่นต้องอยู่ที่ตำแหน่งและทิศทางตอนส่งออก knowledge
ไม่ต้องติ๊ก **เปิด RViz เสริม (ไม่จำเป็น)**; ตัวควบคุมไม่รอ RViz หรือ TF แสดงผลของ RViz

ใช้ CLI ได้เช่นกัน ตรวจเซนเซอร์ก่อนด้วยคำสั่งแรก แล้ว Ctrl+C ก่อนใช้คำสั่งเดินจริง:

```bash
python3 tb3_knowledge/run_knowledge.py --knowledge tb3_knowledge/output/knowledge.json
python3 tb3_knowledge/run_knowledge.py --knowledge tb3_knowledge/output/knowledge.json --drive
```

**หุ่นจะเดินเมื่อข้อมูลพร้อม** โปรแกรมเปิด guard บน notebook ให้อัตโนมัติ ไม่ต้องเปิดแยก
ค่าเริ่มต้น **ชนิด /cmd_vel = auto** โปรแกรมตรวจ subscription ของ driver ก่อนเปิด guard
จึงเลือก `TwistStamped` หรือ `Twist` ตามหุ่นจริง โดยยังไม่สร้าง publisher มอเตอร์ระหว่างตรวจ
หากต้องกำหนดเอง ใช้ `--output-type stamped` หรือ `--output-type twist`
ถ้าเลือกไม่ตรงกับ driver หรือมี subscriber หลายชนิดปนกัน โปรแกรมจะปฏิเสธและแสดงชนิดที่พบ
ค่าความเร็วเริ่มต้น 0.08 m/s และ 0.8 rad/s เป็นตัวอย่าง ต้องตรวจค่าจริงก่อนทดลอง

หากต้องการ RViz เพิ่ม ใช้ checkbox หรือ `--rviz` ข้อมูลที่แสดงเป็นชุดเดียวกับหน้าจอในตัว
ไม่มีการแสดงเส้นทางทั่วสนามที่รับรองว่าอ้อมสิ่งกีดขวางได้ล่วงหน้า
`knowledge_field` ผูกกับ odometry ที่ capture โดยไม่ใช้ AMCL ต่อระหว่างเดิน

หยุดด้วย Ctrl+C หรือ service:

```bash
ros2 service call /knowledge_guard/stop std_srvs/srv/Trigger '{}'
```

หรือ `/knowledge_navigation/stop` ชนิด Trigger เช่นกัน
หลัง stop ให้จบ Program 2 และเตรียม reference ใหม่ก่อนรอบถัดไป
log JSONL อยู่ `output/robot-run.jsonl` เพิ่ม `--log other-run.jsonl` เพื่อแยกไฟล์
สถานะ `arrived_estimate` หมายถึง odometry ประมาณว่าถึง ต้องวัด Goal error จริงแยก

ถ้าสถานะเป็น `full_map_localization_active` แปลว่ายังมี AMCL/SLAM จากช่วงเตรียมทำงานอยู่
ให้หยุดการทดลองใน Program 2 แล้วหยุด Localization ใน Program 1 หรือ terminal ที่เปิด AMCL ไว้
จากนั้นเริ่ม Program 2 ใหม่ สถานะหยุดนี้ล็อกไว้และจะไม่เริ่มเดินเองเมื่อ AMCL หายไป

ตัวรับ LiDAR เก็บสแกนล่าสุดไว้จำนวนจำกัด แล้วเลือกสแกนที่ odometry ครอบคลุมเวลาทั้งรอบแล้ว

วิธีนี้เป็นความจำเซนเซอร์ชั่วคราวระหว่างวิ่ง ไม่ได้อ่านสิ่งกีดขวางจาก knowledge หรือส่งออกประวัตินี้

หากข้อมูลบางมุมยังขาดและยังไม่พบช่องทางเดินตามปกติ แต่ LiDAR ยืนยันทางตรงช่วงสั้นได้

ประกอบด้วยก้าวตรวจอย่างน้อย 0.020 m และระยะสำรองหยุด 0.025 m

ทุกคำสั่งยังตรวจวงหุ่นตลอดแนวเคลื่อนที่ พื้นที่ unknown ขอบสนาม และระยะเบรกตามอายุข้อมูลกับความเร็วที่วัดได้
หาก odometry ยังวัดว่าหุ่นหมุนเร็วกว่า 0.025 rad/s จะสั่งหยุดรอ ก่อนเริ่มขยับตรง

ข้อมูลใหม่ที่ยังมีช่องขาดไม่เริ่มงบระยะใหม่เอง การ pause ไม่ล้างงบระยะหรือเวลา
ช่องสแกนขาดที่ทับวงปลอดภัยด้านหน้ายังคงห้ามเดิน ไม่ใช้แมพสิ่งกีดขวางตัดสินใจ

หากไม่มีทางตรงช่วงสั้นที่ยืนยันได้ แต่หลักฐานเซนเซอร์ยืนยันว่าวงหุ่นรวมระยะเผื่อหมุนได้

คำนวณบริเวณ unknown จากตำแหน่งติดตั้ง LiDAR จริง ไม่ถือว่า NaN เป็นทางโล่ง

ช่องรอยต่อของสแกนที่กว้างขึ้นจากการหมุนถือเป็น unknown เฉพาะมุมนั้น ไม่ขยายความหนาสิ่งกีดขวางทุกทิศ
ช่องรอยต่อที่แคบไม่เกิน 0.20 rad ใช้หลักฐานสแกนสดย้อนหลังตรวจพื้นที่ได้เช่นเดียวกับช่อง NaN
ถ้าหลักฐานไม่ครอบคลุมทั้งช่องและระยะใกล้ ช่องนั้นยังเป็น unknown และยังห้ามหมุนเมื่อทับวงปลอดภัย

## ขอบเขตการตรวจและหยุด

- ตรวจ stamp/frame, scan/odom เก่า, TF mount, scan deskew, odometry กระโดด และ reference ตอนเริ่ม
- Reference มี logical Robot ID และ odometry publisher identity; เป็นการตรวจความต่อเนื่อง ไม่ใช่การยืนยันตัวหุ่นแบบเข้ารหัส
- การยกหุ่นโดยที่ล้อและ odometry ไม่เปลี่ยนอาจตรวจไม่พบ ผู้ใช้ต้อง capture ใหม่เอง
- โปรแกรมไม่ยอม drive จากไฟล์ simulation และไม่ใช้ full-map AMCL/SLAM ช่วยระหว่างเดิน
- PC guard หยุดเมื่อ controller ขาดคำสั่งได้ขณะที่ ROS ยังติดต่อหุ่น
- ถ้า Wi-Fi หลุดหรือคอมดับ คำสั่งหยุดอาจไปไม่ถึง ต้องตรวจ timeout ฝั่ง bringup/OpenCR และมีสวิตช์หยุดที่เข้าถึงได้
- โค้ดและค่าตัวอย่างยังไม่ผ่านการทดลอง/สอบเทียบกับหุ่นจริง
